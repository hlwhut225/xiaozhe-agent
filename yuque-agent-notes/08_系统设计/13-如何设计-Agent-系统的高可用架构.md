# 13. 如何设计 Agent 系统的高可用架构？

## 知识点讲解

### 1. 核心概念

高可用（High Availability）的目标是把系统停机时间降到最低。99.9%（三个九）意味着一年最多停机 8.76 小时，99.99% 是 52.6 分钟，每提升一个九成本和复杂度都会大幅上升。

| 等级 | 可用性 | 年停机时间 |
| --- | --- | --- |
| 99%（2 个九） | 99% | 87.6 小时 |
| 99.9%（3 个九） | 99.9% | 8.76 小时 |
| 99.99%（4 个九） | 99.99% | 52.6 分钟 |
| 99.999%（5 个九） | 99.999% | 5.26 分钟 |

Agent 系统高可用面临一个特殊挑战：依赖外部 LLM API（Claude、OpenAI），这个依赖本身就不是 100% 可用的——API 会有超时、限流、偶发故障。所以不能只考虑自己服务的高可用，还要考虑对外部依赖的容错。

高可用设计的四个核心原则：

1.  **冗余**：关键组件多副本，没有单点故障

1.  **隔离**：一个组件的故障不传播到其他组件（熔断器）

1.  **快速故障转移**：发现故障后自动切换，不需要人工介入

1.  **可观测**：能快速发现和定位故障（监控、告警）

### 2. 技术细节

#### 2.1 无状态设计 + 多副本

Agent 服务必须无状态：会话状态存 Redis，不存进程内存。这样任何一个实例挂掉，负载均衡直接把流量切到其他实例，用户无感知。

#### 2.2 健康检查

三层健康检查：

-   **进程存活**：能响应 HTTP 请求

-   **功能正常**：能成功调用 LLM（发一个简单测试请求）

-   **依赖可达**：Redis、数据库连接正常

负载均衡器（Nginx、Kubernetes）每 10 秒发一次健康检查，连续 3 次失败就把实例摘出去，停止向它路由流量。

#### 2.3 熔断器（Circuit Breaker）

熔断器防止级联故障：当某个下游服务（LLM API、数据库）开始大量报错时，不要继续把请求打过去——一来请求都会失败浪费时间，二来可能把下游压垮。

三个状态：

-   **CLOSED**（正常）：请求正常通过，统计错误率

-   **OPEN**（熔断）：错误率超过阈值，直接拒绝请求，不打下游

-   **HALF\_OPEN**（探测）：熔断一段时间后，放少量请求过去试探，成功则恢复，失败则继续 OPEN

## 面试怎么答

> Agent 系统的高可用要从两个层面考虑：自己服务的高可用，以及对外部 LLM API 依赖的容错。
> 
> 自己服务的高可用：无状态设计是前提——会话状态存 Redis，任何实例挂掉都可以无感知切换；多副本部署，Kubernetes 维持副本数量，实例挂掉自动拉起；健康检查三维度——进程存活、功能正常（能调 LLM）、依赖可达（Redis 通），连续 3 次失败就摘出去不再路由流量。
> 
> 对 LLM API 的容错：熔断器是核心——LLM API 连续 5 次超时或报错就触发熔断，后续请求直接返回错误而不是再打 API，60 秒后自动探测恢复。熔断期间可以返回降级回答（"系统繁忙，请稍后再试"），比让用户等到超时体验要好。

## 高频追问 & 加分点

-   **Q1：依赖的 LLM API 挂了怎么办？** 多 Provider 备份是最可靠的方案：主 Claude，备 GPT-4o，Claude 报错超过阈值自动切换到备用。前提是两个 Provider 的 API 调用方式要统一抽象，切换时应用层感知不到。如果两个都挂了，降级到规则型回答（FAQ 匹配）或者直接告知用户"AI 服务暂时不可用"。

-   **Q2：熔断器的参数（失败阈值、恢复超时）怎么设？** 失败阈值设在 5-10 次——太小容易误触发（LLM API 偶发超时很正常），太大容易放太多失败请求过去。恢复超时设 30-120 秒，取决于下游服务的恢复速度。实际要根据真实的 API 故障特征调整：收集历史故障数据，看平均恢复时间是多少，比那个时间短一点设 timeout。

-   **Q3：Redis 挂了会怎样？怎么保证 Redis 本身高可用？** Redis 挂了会话状态丢失，用户要重新开始对话。缓解方案：Redis Sentinel（主从 + 自动主从切换）或 Redis Cluster（分片 + 高可用）。对于最关键的数据，Redis 只做缓存层，持久化存 PostgreSQL，Redis 挂了从 DB 恢复。另外设 Redis 的 TTL 和内存上限，防止内存打满导致雪崩。

-   **Q4：多可用区部署的数据一致性怎么保证？** 强一致性（同步复制）延迟高，一般用最终一致性。会话状态用 Redis（同一区域内），如果用户请求切换到了另一个区域，会话历史短暂不可用——降级策略是让用户重新开始对话。跨区域同步适合低频的重要数据（用户配置、权限）而不是高频的会话数据。

-   **Q5：可用性 SLA 怎么和业务对齐？** 计算年停机预算：99.9% 是 8.76 小时。把这个小时数分配给不同原因：计划维护（比如 4 小时），故障（比如 4.76 小时）。基于此设计故障检测 + 恢复的时间目标：MTTD（平均检测时间）要在 5 分钟内，MTTR（平均恢复时间）要在 30 分钟内——这样大部分故障的停机时间在 35 分钟以内，一年几次故障加起来不超过 4.76 小时的预算。
