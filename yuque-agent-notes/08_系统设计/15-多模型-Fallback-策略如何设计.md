# 15. 多模型 Fallback 策略如何设计？

## 知识点讲解

### 1. 核心概念

多模型 Fallback 解决的是一个现实问题：没有任何一个 LLM Provider 能保证 100% 可用。Claude API 会有偶发超时，OpenAI 也会有 503。如果系统只依赖一个 Provider，那可用性上限就是那个 Provider 的可用性——通常是 99.9%，意味着一年可能有 8 小时不可用。

多模型 Fallback 的思路是建立一个模型链：主模型失败了，自动切换到备用模型，用户基本无感知。

Fallback 有两类触发条件：

-   **硬失败**：API 超时、返回 5xx 错误、限流 429——这类立即 Fallback

-   **软失败**：输出质量不满足要求（格式错误、长度太短）——这类可以先重试，重试失败再 Fallback

Fallback 链的设计原则：越靠前的模型质量越高、成本越高，越靠后的越便宜快速，最后是兜底的规则型回答。

#### 2.2 超时策略

不同模型设置不同的超时时间：主模型可以等 10 秒，备用模型只等 5 秒，因为切到备用说明系统已经有压力了，不能再慢了。

#### 2.3 失败统计和自动禁用

如果某个模型在最近 5 分钟内失败率超过 50%，就临时禁用它，等一段时间后再尝试恢复。不要在一个已经大概率失败的模型上反复重试。

## 面试怎么答

> 多模型 Fallback 的核心是建立一个有优先级的模型链，主模型失败自动切换到备用，用户无感知。
> 
> 触发条件分两类：硬失败（超时、5xx、429）立即切换，不重试——因为重试同一个模型大概率还是失败，浪费时间；软失败（输出格式不对、质量不达标）先重试 1-2 次，重试失败再切换。
> 
> 每个模型要维护成功/失败计数，失败率超过 50% 就临时禁用 5 分钟，避免反复在一个已经挂了的模型上重试。同时记录"用了哪个模型"的指标——如果发现 Fallback 频率很高，说明主模型有问题，需要排查。

## 高频追问 & 加分点

-   **Q1：Fallback 到质量更低的模型，用户会感知到质量下降吗？** 取决于任务类型。简单问答（分类、提取）Haiku 和 Sonnet 差别不大，用户感知不到；复杂推理、长文本分析差别就很明显。所以 Fallback 策略最好按任务类型区分——简单任务的 Fallback 链可以直接到便宜模型，复杂任务的 Fallback 要保守，降级到中等模型，不能直接跳到最便宜的。

-   **Q2：多 Provider Fallback 有什么坑？** API 格式不统一——Claude 和 OpenAI 的请求/响应格式不同，需要统一抽象。另外要注意 system prompt 的行为可能不同，同样的 prompt 在 Claude 和 GPT-4o 上效果可能有差异，Fallback 后输出风格会变化。最好针对每个 Provider 分别测试 prompt 效果，或者用 LangChain 这类做了统一抽象的框架。

-   **Q3：Fallback 应该对用户透明吗？** 内部透明（日志里记录用了哪个模型），对用户可以不透明——用户不需要知道后台换了什么模型。但如果降级影响了输出质量（比如从 Sonnet 降到 Haiku，某些复杂问题可能回答变简单），可以加一行提示："当前使用简化模式，如需更详细的分析请稍后重试"。

-   **Q4：Fallback 和 A/B 测试怎么区分？** Fallback 是被动的：主模型出了问题才切，目的是保可用性。A/B 测试是主动的：主动把流量分给两个模型，目的是比较哪个更好。两者可以同时存在——正常情况下 A/B 测试路由流量，某个模型出问题时 Fallback 自动切走，保证测试不会因为模型故障而损失流量。

-   **Q5：如何监控 Fallback 的频率？** 在每次 LLM 调用结果里记录 model\_used 字段，汇总到监控系统。关键指标：主模型命中率（正常应该 > 95%）、各备用模型的使用频率、Fallback 的原因分布（超时 vs 错误 vs 质量不达标）。主模型命中率持续低说明主模型有系统性问题，需要排查是限流、服务故障还是 prompt 问题。
