# 14. 如何实现 Agent 的可观测性（Observability）？

## 知识点讲解

### 1. 核心概念

可观测性（Observability）是回答"这个系统现在怎么了"的能力。对传统 Web 服务，可观测性已经有成熟的方法论：Logs + Metrics + Traces。Agent 系统同样需要这三层，但有 Agent 特有的复杂性。

Agent 可观测性为什么更难：

-   **非确定性**：同样的输入可能产生不同的执行路径，"这次为什么走了这条路"很难事后复原

-   **执行跨度大**：一次 Agent 任务可能调用 10 个工具、产生 30 次 LLM 调用，链路很长

-   **成本可见**：LLM 调用有直接的货币成本，必须实时追踪，不然账单来了才发现炸了

### 2. 技术细节

#### 2.1 三层可观测性的 Agent 实现

**Logs（日志）**：记录每次执行的详细过程，用于事后调试

**Metrics（指标）**：持续收集聚合数据，用于趋势分析和告警

**Traces（追踪）**：串起一次完整任务的所有步骤，用于跨系统的链路分析

#### 2.2 关键指标监控清单

| 指标 | 监控频率 | 告警阈值参考 | 用途 |
| --- | --- | --- | --- |
| 任务成功率 | 实时 | < 95% 告警 | 质量基准 |
| P95 延迟 | 实时 | > 30s 告警 | SLA 保障 |
| 单次任务成本 | 实时 | > $1 告警 | 成本控制 |
| LLM API 错误率 | 实时 | > 1% 告警 | 供应商可用性 |
| 工具调用失败率 | 5 分钟 | > 5% 告警 | 工具健康度 |
| Token 日消耗 | 每日 | 环比 > 20% 告警 | 异常使用检测 |

### 3. 对比与拓展

可观测性工具选型：日志用结构化格式（JSON）+ ELK/Loki；指标用 Prometheus + Grafana；链路追踪用 OpenTelemetry（厂商无关，支持 Jaeger/Zipkin/DataDog）。Agent 专属的工具有 LangSmith（LangChain 生态）和 Weights & Biases（更偏 ML 实验追踪）。

## 面试怎么答

> Agent 可观测性和传统服务一样，围绕 Logs、Metrics、Traces 三层，但有 Agent 特有的内容。Logs 要记录每次 LLM 调用的 prompt/completion、每次工具调用的输入输出，用 trace\_id 串联整个任务链路；Metrics 要追踪成功率、延迟、token 消耗和成本——成本是 Agent 特有的，传统服务没有这个；Traces 要跨多个 Agent、多个工具，形成完整的调用链。
> 
> 实现上，我会用一个 AgentObserver 类封装所有可观测性逻辑，在 Agent 的关键点注入（任务开始/结束、每次 LLM 调用、每次工具调用）。这样可观测性和业务逻辑解耦，改业务不影响监控，换监控后端也不影响业务。
> 
> 最容易忽视的是成本监控——每次 LLM 调用要实时累积成本，设置告警阈值。没有成本监控的 Agent 系统，等月底账单来了才知道哪里炸了，已经晚了。

## 高频追问 & 加分点

-   **Q1：日志里包含 prompt 内容会不会有隐私风险？** 会。处理方式：写日志前脱敏（用正则把手机号、邮箱、身份证号替换掉）；只记录 prompt 的摘要或哈希而不是全文；区分不同日志级别（DEBUG 级别记全量，INFO 级别记摘要，INFO 才推送到集中日志系统）；对日志存储做访问控制（只有有需要的人才能看完整日志）。

-   **Q2：可观测性工具本身会不会影响 Agent 性能？** 会，但可以控制。同步写日志影响最大，要改成异步写（把日志条目放队列，后台线程写）；指标采集用内存聚合（不每次都写 DB）；链路追踪用采样（比如只记录 10% 的请求的完整 trace）。性能敏感的路径只做轻量监控，重量级可观测性只对采样出来的请求做。

-   **Q3：如何发现 Agent 的"慢"在哪里？** 在每个步骤加计时。通常 Agent 的延迟分布是：等 LLM 响应（最大头，通常 1-10 秒）、工具执行（差异大，网络工具几秒，计算工具可能几十秒）、框架开销（通常 < 100ms，不是瓶颈）。有了步骤级别的计时数据，P95 延迟高的话，能直接定位到哪个步骤是瓶颈。

-   **Q4：多 Agent 系统的 trace 如何串联？** 关键是 trace\_id 的传播：Orchestrator Agent 生成 trace\_id，把它传给每个 Worker Agent；Worker Agent 的所有日志都带上这个 trace\_id。这样查日志时，搜 trace\_id 就能看到整个多 Agent 任务的完整执行链路，不需要靠时间戳猜哪些日志属于同一次任务。

-   **Q5：如何设置合理的成本告警阈值？** 用历史数据确定基准：跑 1000 次典型任务，计算平均成本和 P95 成本。告警阈值设在 P95 的 1.5-2 倍（允许一定波动，但异常增长时触发告警）。另外设置总量告警（比如单日总成本超过预算的 80% 时告警），这样能发现系统性的异常而不只是单次请求的异常。
