# 11. DAG 和循环流在 Agent 工作流中如何选择？

## 知识点讲解

### 1. 核心概念

DAG（有向无环图）和循环流是描述 Agent 工作流拓扑结构的两种基本模式，选哪种本质上是在**可预测性**和**灵活性**之间取舍。

**DAG 的思维模型**：提前规划好所有路径。就像写一张地图——从哪里出发，可能经过哪些路口，可以走哪些分支，但不允许走回头路。整个执行路径在写代码时就确定了，运行时只是沿着预设的路走。

**循环流的思维模型**：边做边调整。就像人解决一道难题——试一次，看看结果，不满意就再试一次，直到满意为止。执行了几次、走了哪条路，要到运行时才能知道。

这个区别直接影响系统的可测性、成本可控性和调试难度。

#### 2.4 选型判断标准

| 场景特征 | 推荐结构 |
| --- | --- |
| 流程步骤固定，无需回头 | DAG |
| 有明确的质量标准，需要迭代优化 | 循环流 |
| 需要精确控制成本和延迟 | DAG（执行路径可预测） |
| 处理开放式、结果不确定的任务 | 循环流（带终止条件） |
| 流程复杂但部分步骤需要重试 | 混合（DAG 主结构 + 节点内部循环） |

### 3. 对比与拓展

一个常见的实践是：**先用 DAG 设计，发现哪些节点需要重试/迭代，再局部引入循环**。而不是一开始就用完全开放的循环流——循环流的成本和执行时间难以预测，线上系统的 SLA 可能无法保证。

## 面试怎么答

> DAG 和循环流的核心区别是可预测性：DAG 的执行路径在设计时就能推断出来，成本和延迟有边界；循环流的执行路径是运行时决定的，要试几次才知道。
> 
> 选型原则：流程固定、对延迟和成本有明确要求，用 DAG；任务是开放式的、需要迭代优化直到满足某个标准，用循环流——但一定要有硬终止条件（最大迭代次数或成本预算），不加的话生产上很容易出问题。
> 
> 实际工程里用混合方案最多：外层是 DAG，某些节点内部包含小循环（比如搜索不到结果就换关键词再搜），这样外层流程可预测，内层有一定的自适应能力。

## 高频追问 & 加分点

-   **Q1：循环流如何保证一定会终止？** 三道防线：最大迭代次数（比如最多循环 5 次，到了就强制停止）；成本预算（累计 token 超过上限就停）；时间限制（超过 N 秒强制终止）。三个条件任意一个触发都终止，不能只靠 LLM 自己判断完成——LLM 可能永远输不出"完成"信号。

-   **Q2：DAG 能处理"失败了重试"的场景吗？** 能，但需要在节点内部做，而不是在 DAG 层面做。DAG 节点可以内部实现重试逻辑（try 3 次），对外仍然是一个节点。如果 3 次都失败，节点可以抛出异常或返回降级结果。DAG 结构本身不变，可预测性不受影响。

-   **Q3：LangGraph 支持真正的无限循环吗？** 支持，但不建议用于生产。LangGraph 允许条件边指向已经执行过的节点（形成循环），没有框架层面的硬限制。所以终止条件完全靠开发者在路由函数里实现。最佳实践是在 State 里记录迭代次数，路由函数检查迭代次数作为退出条件。

-   **Q4：如何估算循环流的平均成本？** 用统计方法：跑 100 次典型任务，记录每次的实际迭代次数，算出均值和 P95。然后用"平均迭代次数 × 单次迭代成本"估算平均成本，用 P95 迭代次数估算最坏情况成本。这个数据也是设置"最大迭代次数"的参考依据——如果 P95 是 4 次，设置上限 6 次是合理的。

-   **Q5：有没有不适合用 DAG 也不适合用循环流的场景？** 有——真正的多 Agent 并发协作（多个 Agent 同时工作、相互通信、动态协调）用 DAG 和单一循环流都很难表达，需要更复杂的编排机制（消息队列、事件驱动）。这类场景通常需要自研或者用专门支持并发 Agent 的框架（比如 Microsoft AutoGen 的 GroupChat 模式）。
