# 13. 如何构建一个 Agent Pipeline？

## 知识点讲解

### 1. 核心概念

Agent Pipeline 是把多个处理步骤串联起来的数据流架构：每个步骤产出一个结果，作为下一步的输入，最终形成完整的输出。

和工作流（Workflow）的区别：Pipeline 强调**单向数据流动**，通常是线性或 DAG 结构；工作流可以包含循环、人工介入、状态回溯等更复杂的控制流。Pipeline 是工作流的一种简化形式，适合流程清晰、数据流向确定的场景。

构建可靠 Pipeline 的关键不是代码多复杂，而是**把每个步骤的输入输出格式定义清楚**——格式清晰了，步骤之间的契约就清晰了，测试和调试才容易。

### 3. 对比与拓展

Pipeline 设计的关键原则：**格式契约优先**。步骤之间的数据格式（TypedDict 或 Pydantic）要先定义清楚，再实现步骤逻辑。格式清晰后，每个步骤可以独立开发和测试，也容易替换某个步骤的实现而不影响其他步骤。

## 面试怎么答

> Agent Pipeline 的核心是单向数据流——每个步骤接收上游的输出，做自己的处理，把结果传给下游。构建 Pipeline 最重要的是先定义好每个步骤的输入输出格式，用 TypedDict 或 Pydantic 强制约束，这样步骤之间的契约就清晰了。
> 
> LangGraph 的 StateGraph 是目前构建 Pipeline 最合适的工具：节点是处理函数，边是数据流，条件边可以实现分支路由，整个 Pipeline 的结构一目了然。
> 
> 性能优化上两个主要手段：缓存（相同输入不重复处理）和并行（独立的步骤或批量任务并发执行）。另外，每个步骤要有错误处理和降级逻辑——不能让一个步骤的失败把整个 Pipeline 搞崩。

## 高频追问 & 加分点

-   **Q1：Pipeline 里如何做流式输出，让用户实时看到进度？** LangGraph 支持 .stream() 模式，每个节点完成时会发出一个事件，可以通过 Server-Sent Events 推送到前端。前端可以实时显示"正在搜索..."、"正在分析..."这样的进度状态。关键是 Pipeline 的步骤边界和前端的 UI 状态要对应，用户能看到有意义的进度，而不只是一个转圈圈。

-   **Q2：Pipeline 的步骤失败后如何重试？** 两种方式：步骤内部重试（try 3 次，指数退避）和 Pipeline 级别重试（把整个 Pipeline 重新跑，从失败的步骤开始）。后者需要 Pipeline 支持"从某个检查点恢复"，LangGraph 支持 checkpointing，可以保存中间状态，失败后从最近的检查点恢复，而不用从头跑。

-   **Q3：多个 Pipeline 实例并发时，如何避免资源竞争？** 每个 Pipeline 实例有独立的 State 对象，不共享状态，所以数据层面没有竞争。资源竞争主要在外部：LLM API 的速率限制（用信号量控制并发数）、共享数据库的写入（用乐观锁或队列串行化写入）、缓存的读写（用带 TTL 的分布式缓存，不用本地缓存）。

-   **Q4：如何测试 Pipeline 的各个步骤？** 分层测试：单元测试每个步骤函数（mock 掉 LLM 调用和外部工具，输入固定，验证输出格式和关键内容）；集成测试跑完整 Pipeline（用便宜的模型，固定测试用例，验证端到端结果）；回归测试（每次修改 Pipeline 都跑完整测试集，防止改坏了之前好的场景）。

-   **Q5：Pipeline 的版本管理怎么做？** Pipeline 的变更主要有三类：加新步骤（通常向后兼容）、改现有步骤逻辑（需要完整测试）、改 State 字段结构（最危险，可能破坏存量数据）。建议用语义化版本号标记 Pipeline（v1.0、v1.1），State 结构变更要有迁移脚本，同时支持新旧两个版本并行运行一段时间，确认新版没问题后再下线旧版。
