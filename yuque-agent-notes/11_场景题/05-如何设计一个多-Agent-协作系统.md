# 5. 如何设计一个多 Agent 协作系统?

## 知识点讲解

### 1. 核心概念

多 Agent 系统的核心问题不是"怎么让多个模型一起跑"，而是**怎么把复杂任务分给合适的 Agent，怎么协调它们的执行，怎么把结果整合起来**。

什么时候值得用多 Agent？当单个 Agent 的 context 装不下所有需要的工具和上下文、或者任务的不同阶段需要不同的专业能力时。一个 Agent 做所有事，prompt 会越来越臃肿，效果反而变差。

### 2. 技术细节

#### 2.1 Orchestrator 模式

核心架构：一个 Orchestrator Agent 负责拆任务、分配、收集结果；多个 Worker Agent 各司其职。

Orchestrator 的职责：

-   把用户请求拆成子任务

-   决定哪个 Agent 做哪个任务

-   管理任务的执行顺序（顺序/并行/条件）

-   聚合各 Agent 的结果

-   处理 Agent 失败和重试

Worker Agent 的设计原则：**职责单一，接口清晰**。每个 Worker 有固定的输入格式和输出格式，不依赖其他 Worker 的内部状态。

#### 2.2 任务调度策略

| 策略 | 适用场景 | 特点 |
| --- | --- | --- |
| 顺序执行 | 有依赖关系的任务 | B 依赖 A 的结果 |
| 并行执行 | 独立任务 | 减少总时间 |
| 条件执行 | 分支场景 | 基于 A 的结果决定是否执行 B |
| 扇出-聚合 | 需要多视角的任务 | 多个 Agent 独立分析，最后合并 |

#### 2.3 共享状态管理

所有 Agent 共享一个状态库，存储：

-   任务元数据（ID、状态、依赖关系）

-   Agent 执行结果（按任务 ID 索引）

-   全局上下文（对所有 Agent 都需要的信息）

写操作需要加锁，防止并发写冲突。只允许 Orchestrator 修改任务状态，Worker 只读任务、写结果。

## 面试怎么答

> 多 Agent 系统的核心是 Orchestrator 模式：一个 Orchestrator 负责拆任务、分配、调度和聚合；多个专业 Worker 各负责一个领域。
> 
> 关键设计点有三个：① Worker 职责单一、接口清晰，输入输出格式固定，不依赖其他 Worker 的内部状态；② 任务调度策略要根据依赖关系决定顺序/并行——有依赖关系的顺序执行，独立的并行执行；③ 共享状态管理，所有任务结果集中存储，Worker 之间通过共享状态传递信息，不直接互相通信。
> 
> 什么时候用多 Agent？当单个 Agent 的工具集太多导致 prompt 膨胀、或者任务的不同阶段需要完全不同的"心智模式"时。不要为了多 Agent 而多 Agent，增加协调复杂度是有成本的。

## 高频追问 & 加分点

-   **Q1：多个 Agent 给出冲突结论时怎么处理？** 几个策略：① Orchestrator 汇总所有 Agent 的结论，明确展示分歧，让用户或上级决策；② 多数投票（适合分类判断）；③ 按优先级取权威 Agent 的结论（比如某任务以分析 Agent 的结论为准）。对于高风险决策，分歧应该直接上报，不要自动解决。

-   **Q2：某个 Worker Agent 挂了怎么处理？** 两层处理：Worker 层做超时检测和重试（最多 2 次）；Orchestrator 层对失败的 Worker 有降级策略，比如跳过可选步骤、用简化版本替代、或者返回"部分完成"的结果附上说明。不要让单个 Worker 的失败导致整个流程阻塞。

-   **Q3：多 Agent 系统的调试比单 Agent 困难很多，怎么办？** 可观测性是关键：每个 Agent 的输入、输出、执行时间都要记录；任务调度日志（谁在什么时间执行了什么）要完整；失败时要记录是哪个 Agent 失败的以及完整的错误信息。有了这些，排查时可以把特定 Agent 的输入/输出单独拿出来复现，不需要重跑整个流程。

-   **Q4：多 Agent 比单 Agent 成本更高怎么控制？** 对于简单任务，Orchestrator 在拆分阶段就判断"这个任务不需要多 Agent"，直接走单 Agent 路径。Worker 之间传递的上下文要做摘要，不传全文。并行的 Worker 可以用更便宜的小模型，Orchestrator 和最终综合步骤才用大模型。
