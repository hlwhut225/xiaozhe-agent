# 15. 如何设计生产级别的 Agent 系统

## 知识点讲解

### 1. 核心概念

生产级别的 Agent 系统和 Demo 的本质区别：Demo 只要能跑，生产系统还要能**稳定跑、出了问题能发现、发现了问题能定位、定位了问题能恢复**。

生产系统的四个核心维度：

| 维度 | 核心问题 | 关键手段 |
| --- | --- | --- |
| 可靠性 | 出错了还能继续吗 | 重试、熔断、降级 |
| 可观测性 | 发生了什么我知道吗 | 结构化日志、指标监控、链路追踪 |
| 安全性 | 有没有被滥用或攻击 | 认证授权、输入验证、速率限制 |
| 可维护性 | 出了问题能快速修 | 模块化设计、完整文档、可回滚 |

### 2. 技术细节

#### 2.1 请求链路设计

每个环节都要有 trace\_id 贯穿，日志里带上 trace\_id，出了问题才能把整个请求链路串起来。

#### 2.2 可观测性三要素

**结构化日志**：用 JSON 格式记录，包含 trace\_id、用户 ID、任务类型、执行时间、成功/失败、工具调用次数。不要用自由文本，结构化数据才能被日志系统索引和查询。

**指标监控**：

-   业务指标：任务成功率、平均完成时间、工具调用次数

-   系统指标：API 延迟（P50/P95/P99）、错误率、缓存命中率

-   成本指标：Token 消耗量、每次请求成本

**链路追踪**：每次工具调用都记录（工具名、入参、出参、耗时），方便复现问题时还原完整执行链路。

#### 2.3 安全设计

-   **认证授权**：API Key 或 OAuth，限制哪些用户可以调用哪些 Agent

-   **速率限制**：每用户每分钟最多 N 次请求，防止滥用和成本失控

-   **输入验证**：输入长度限制（防止 context 爆炸）、关键词检测（防注入）

-   **最小权限**：Agent 只开放必要的工具，高风险工具（删除数据、发邮件）需要额外权限

#### 2.4 部署与运维

-   **配置外置**：System Prompt、工具列表、温度参数不要硬编码，用环境变量或配置文件管理

-   **灰度发布**：新版本先给 5% 用户，监控指标正常再逐步扩量

-   **快速回滚**：保留上一版本配置，出问题能在 5 分钟内回滚

## 面试怎么答

> 生产级 Agent 系统和 Demo 的核心差距在于：能不能在出了问题的时候快速发现、定位和恢复。
> 
> 四个维度要做好：可靠性（重试、熔断、降级）、可观测性（结构化日志 + 指标 + 链路追踪）、安全性（认证授权、速率限制、输入验证）、可维护性（配置外置、灰度发布、快速回滚）。
> 
> 可观测性是我认为最被低估的维度。每个请求要有 trace\_id 贯穿，记录输入、执行步骤、工具调用、输出、耗时。没有这些数据，出了问题只能靠猜；有了这些数据，大多数问题能在 10 分钟内定位。
> 
> 安全上两个重点：速率限制（防止单个用户把成本刷爆）和输入验证（防止 Prompt 注入）。这两个不难实现，但不做的话早晚会出事。

## 高频追问 & 加分点

-   **Q1：如何设计告警体系，避免告警疲劳？** 告警要和业务指标直接挂钩，不要告警过于敏感的系统指标。实践上：① 任务成功率连续 5 分钟低于 90% → 紧急告警；② P99 延迟超过 SLA 上限 → 警告；③ 成本超过日预算 80% → 提醒。告警要有分级（紧急/警告/信息），紧急的要叫醒人，信息的只发邮件。定期审查告警触发记录，删除噪音告警。

-   **Q2：Agent 的配置（System Prompt）发生 bug，如何快速回滚？** System Prompt 和其他配置要版本化管理（和代码一样用 git），每次发布有版本号。回滚就是把配置版本切回上一个稳定版本，不需要重新部署代码。另外，新配置上线要走灰度：5% 用户先用新配置，监控 15 分钟，没有异常再逐步扩量到 100%。这样配置 bug 的影响范围被限制在 5% 用户内。

-   **Q3：多租户场景（不同客户的 Agent 配置不同）怎么设计？** 每个租户有独立的配置（System Prompt、工具集、限流配置），存在配置服务里。执行时按 tenant\_id 拉取对应配置，不同租户的数据隔离（日志、指标都带 tenant\_id）。计费按 tenant 维度统计。关键是租户间的资源隔离——一个租户的高流量不能影响其他租户，需要在限流层做租户级别的隔离。

-   **Q4：Agent 系统上线前，有哪些关键验收标准？** 我通常看这几个：① 成功率测试集 > 95%；② P95 延迟在 SLA 以内；③ 错误处理覆盖（模拟 API 超时、工具失败、恶意输入，验证降级行为）；④ 成本预算合理（预估月均成本 + 峰值上限）；⑤ 告警能正常触发；⑥ 日志可以完整重现一个请求的执行链路。这六个标准过了，才算准备好上生产。
