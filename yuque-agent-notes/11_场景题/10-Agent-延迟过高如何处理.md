# 10. Agent 延迟过高如何处理

## 知识点讲解

### 1. 核心概念

Agent 延迟高，先找瓶颈，再对症下药。延迟分解：

-   **LLM 推理**：通常 1-5 秒，占总延迟最大头（50-60%）

-   **工具调用**：数据库查询、外部 API，可能 0.5-3 秒（20-30%）

-   **串行等待**：前一步没完成就不能开始下一步

-   **网络传输**：通常 < 200ms，但高并发时会上升

不同瓶颈的解法完全不同，不分析就优化是在瞎折腾。

### 2. 技术细节

#### 2.1 五种优化策略

**策略 1：流式输出（Stream）** 不等完整响应，收到第一个 token 就开始展示。用户感知延迟从"等待全部生成完"变成"等待第一个字出现"，体感延迟大幅降低。

**策略 2：并发工具调用** Agent 的工具调用默认串行——调完 A 才能调 B。如果 A 和 B 相互独立，改成并发调用，总时间从 T(A)+T(B) 变成 max(T(A), T(B))。减少 30-50% 的工具延迟。

**策略 3：更快的模型** 对于不需要最强推理能力的任务，用延迟更低的模型（比如 claude-3-haiku 比 claude-3-sonnet 快 2-3x）。

**策略 4：语义缓存** 重复或相似的请求直接返回缓存，延迟从 2-5 秒变成 < 50ms。

**策略 5：预加载** 可以预测的数据提前加载——比如用户打开页面时就开始拉取可能需要的上下文，不等用户开口再加载。

#### 2.2 延迟优化的优先级

流式输出和并发工具调用投入产出比最高，先做这两个。

#### 2.3 首字节延迟 vs 完整延迟

对用户体验来说，首字节延迟（TTFB，Time to First Byte）比完整生成时间更重要。流式输出是降低 TTFB 的核心手段。

## 面试怎么答

> Agent 延迟高，先做分析再优化。延迟主要来自三块：LLM 推理（50-60%）、工具调用（20-30%）、网络（10%）。找到瓶颈再对症。
> 
> 投入产出比最高的两个手段：流式输出（把用户感知延迟从"等全部生成完"变成"等第一个字"，体感差距很大）；并发工具调用（把串行的工具调用改成并发，总时间从各工具耗时之和变成最慢那个，减少 30-50%）。
> 
> 模型选择也很重要——不是所有任务都需要最强模型。简单查询用快速小模型，延迟可以低 2-3x。配合语义缓存，重复请求直接返回，延迟从秒级降到毫秒级。

## 高频追问 & 加分点

-   **Q1：流式输出会不会影响答案质量？** 不会。流式只是改变了返回方式，推理过程完全相同。模型生成完整答案，只是逐 token 返回而不是等全部生成完再返回。对 token 采样和推理没有任何影响，答案质量完全一样。

-   **Q2：并发工具调用怎么处理有依赖关系的工具？** 有依赖关系的必须串行：B 需要 A 的结果，那 A → B 不能并发。只对独立的工具做并发。设计时要分析工具依赖图（DAG），识别哪些工具可以并发，哪些必须顺序。复杂场景可以用任务调度框架（比如 asyncio.gather 配合依赖管理）自动处理。

-   **Q3：缓存命中率低，语义缓存怎么做？** 把历史请求向量化存入向量库，新请求来了先做相似度检索。设阈值（比如 0.95），高于阈值直接返回缓存。缓存除了存结果，还要存请求的向量表示和 metadata（时间戳、模型版本、使用次数）。过期策略：超过 N 天或底层数据更新了就失效。

-   **Q4：SLA 怎么设置，破线了怎么处理？** SLA 根据业务场景定：实时对话 P95 < 2s，分析报告 P95 < 10s。监控分位数（P50/P95/P99），不只看平均值——平均值掩盖了尾部延迟。破线触发告警，工程师介入排查。如果是突发流量导致，自动扩容或启用流量削峰（队列化低优先级请求）。
