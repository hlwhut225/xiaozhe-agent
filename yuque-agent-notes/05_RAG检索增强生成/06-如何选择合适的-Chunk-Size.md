# 6. 如何选择合适的 Chunk Size？

## 知识点讲解

### 1. 核心概念

Chunk Size 选择的本质是在两个方向上找平衡：

**块太小** → 语义碎片化，单块信息不完整，检索时需要更多块才能覆盖一个完整概念，top-K 里塞进来的信息密度低

**块太大** → 向量表示是"多个主题的平均"，检索精度下降；注入 LLM 的 token 更多，成本升、质量不一定升

没有一个"正确答案"，但有几个因素可以帮你缩小范围。

### 2. 技术细节

#### 2.1 影响 Chunk Size 的五个因素

**① 文档类型**

不同文档的信息密度和结构差异很大：

| 文档类型 | 推荐 chunk_size | 理由 |
| --- | --- | --- |
| 代码文件 | 512-768 token | 函数/方法是自然单元，不能断 |
| 技术文档 / 知识库 | 768-1024 token | 一个概念通常在一段内 |
| 新闻 / 博客 | 512-768 token | 段落短，保持完整即可 |
| 法律 / 合同 | 1024-2048 token | 条款相互关联，需要上下文 |
| 对话记录 | 256-512 token | 每轮是自然边界 |

**② LLM 上下文窗口 + Top-K**

所以 chunk\_size 设 1024-1200 是合理的，不会超限。

**③ 查询类型**

-   事实性问题（"XXX 是什么"）→ 小块，精准定位即可

-   综合性问题（"分析 XXX 的利弊"）→ 大块，需要更多上下文

**④ Embedding 模型的上限**

大多数 embedding 模型有 512 token 上限（如 all-MiniLM），超出的内容被截断——chunk\_size 超过模型上限等于白设。用 OpenAI text-embedding-3 系列上限是 8191 token，这个就不是瓶颈了。

**⑤ 评估指标反馈**

这是最终裁判。上面的因素帮你定范围，实际最优值要靠在评估集上跑指标来确定。

#### 2.2 Overlap 的设置

Overlap 解决边界信息丢失问题。一句话被切断，两个 chunk 各有一半——overlap 让两边都包含完整的这句话。

经验值：**overlap = chunk\_size 的 10-20%**。设太大（>30%）则检索时大量重复，top-K 里独立信息密度下降。

#### 2.3 动态 Chunk Size

不同文档类型混在同一个知识库时，统一设置一个 chunk\_size 往往不够好。更好的做法是按文档类型分别设置，或者先做语义分块（自然边界），再做 token 上限裁剪。

## 面试怎么答

> Chunk Size 没有通用最优值，但选择它有一个框架：先用文档类型确定范围（代码 512-768、普通文档 768-1024、法律文件 1024-2048）；再用 context\_window 和 top\_k 算出上限（available\_tokens / top\_k 就是单块上限）；最后在评估集上跑 A/B 测试确认。
> 
> 两端的坑：太小了语义碎片化，单块不包含完整概念，检索时需要大量 top-K 才能覆盖，信息密度低；太大了向量是多个主题的平均，精准度下降，而且 chunk 数量少了，recall 也未必好。实践里 768-1024 token 是大多数场景的合理起点。
> 
> 另外 overlap 不要忘了，设 chunk\_size 的 10-20%，防止边界信息被切断。混合文档类型的知识库最好按类型分别设置，不要一刀切。

## 高频追问 & 加分点

-   **Q1：怎么判断当前 chunk\_size 是不是太小了？** 看 top-K 检索结果里的重复率。如果 5 个返回结果里有 3 个内容几乎一样（来自同一段落的相邻小块），说明粒度太细，信息密度低，应该调大。

-   **Q2：chunk\_size 和 Recall@K 的关系是什么？** 不是线性的。在某个最优点附近，召回率最高；太小了单块缺上下文、召回率下降；太大了单块语义模糊、精准度下降。这个最优点因数据集而异，只能实测。

-   **Q3：embedding 模型 token 上限怎么处理？** chunk\_size 不能超过 embedding 模型的 token 上限（如 all-MiniLM 是 512），否则超出部分被截断，向量表示的是部分内容。如果用 OpenAI text-embedding-3 这类上限大的模型，这个限制就不那么严了。总之建议 chunk\_size ≤ embedding 模型上限的 80%，留点余量。

-   **Q4：上线后能动态调整 chunk\_size 吗？** 调整 chunk\_size 意味着需要重新分块 + 重建向量索引，成本较高。建议上线前多花时间在离线评估上找到合理参数。如果必须调，增量更新（只处理变化的文档）比全量重建经济。

-   **Q5：多语言知识库 chunk\_size 怎么设？** 中文和英文的 token 密度不同——中文每个字符约 0.5-1 token，英文每个单词约 1-2 token。如果按字符数设 chunk\_size，中英文实际 token 数差异会很大。建议统一用 token 计数器（如 tiktoken）作为 length\_function，保证不同语言的 chunk token 数一致。
