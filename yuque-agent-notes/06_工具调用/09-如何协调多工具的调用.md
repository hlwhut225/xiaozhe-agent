# 9. 如何协调多工具的调用？

## 知识点讲解

### 1. 核心概念

Agent 在一次任务里通常要调用多个工具。协调这些工具调用有两个核心问题：**顺序**（谁先谁后）和**并行**（能不能同时跑）。

工具之间的依赖关系决定了执行顺序：

-   **无依赖**：工具 A 和工具 B 的输入互不影响——可以并行，总耗时是单个工具的最长时间

-   **有依赖**：工具 B 的输入依赖工具 A 的输出——必须串行，总耗时是两者之和

-   **条件依赖**：根据工具 A 的结果决定是否调用工具 B

LLM 本身可以做工具协调决策：模型在一轮推理里可以一次性生成多个工具调用（并行信号），也可以在看到上一个工具结果后再决定下一步（串行信号）。但 LLM 只负责"决策"，Agent 框架负责"执行"。

### 2. 技术细节

#### 2.1 并行工具调用

当 LLM 在一轮响应里返回多个 tool\_use block（Anthropic）或多个 tool\_calls（OpenAI），这是并行调用信号。Agent 框架应该用线程池或 asyncio 并发执行这些工具，而不是串行执行。

串行执行 N 个无依赖工具的总耗时是各工具耗时之和；并行执行只需要最慢那个工具的耗时。对于延迟敏感的场景，这个优化非常值得做。

#### 2.2 串行调用链

有些任务天然是串行的：先搜索 → 根据搜索结果查数据库 → 根据数据库结果生成报告。每一步的工具输出是下一步的输入。

这种情况下不需要特殊设计，Agent 的标准循环（工具结果返回给模型 → 模型继续推理）自然就是串行的。

#### 2.3 工具调用次数控制

Agent 可能陷入循环（反复调用同一个工具但结果没有进展），也可能任务特别复杂导致工具调用次数暴增。两种情况都需要加保护：

-   设置最大工具调用轮数（比如 10 轮）

-   检测循环（连续 3 次调用同一工具且参数相同，判定为循环）

-   超出上限后返回当前最好的结果或报告无法完成

## 面试怎么答

> 多工具协调的核心是区分"能并行的"和"必须串行的"。判断方法很直接：工具 B 的输入是否依赖工具 A 的输出——如果是，就串行；如果不是，就并行。
> 
> LLM 本身会做这个判断：如果模型在一轮推理里返回多个工具调用，就是并行信号，Agent 框架用线程池或 asyncio 并发跑这些工具，总耗时降为最慢那个工具的时间而不是所有工具时间之和。串行的情况下，每轮工具结果返回给模型，模型根据结果决定下一步，标准的 Agent 循环本来就是这个节奏。
> 
> 还有两个工程上必须做的保护：设置最大工具调用轮数（防止任务复杂度失控）；循环检测（连续多次调用同一工具但参数和结果没变，直接中断并返回当前状态）。没有这两个保护，Agent 在边界情况下会无限跑下去。

## 高频追问 & 加分点

-   **Q1：LLM 怎么知道哪些工具可以并行？** 模型通过工具的描述和上下文来推断。好的工具 description 会说明"此工具需要先调用 X 获取 user\_id"这样的依赖提示。如果描述清晰，模型通常能正确地在一轮里调用多个无依赖的工具。也可以在 system prompt 里加"当多个工具互不依赖时，一次性调用所有工具"的显式指令。

-   **Q2：并行工具调用有哪些限制？** 外部 API 的速率限制是最常见的瓶颈（同时打 5 个搜索 API 请求可能触发限速）；数据库连接池限制（并发查询太多会排队）；工具内部有状态（同时写同一个文件会冲突）。实现时要根据工具类型设置并发上限。

-   **Q3：工具调用结果有错误，其他并行工具的结果还用吗？** 用。并行调用中，一个工具失败不影响其他工具的结果。把成功的结果和失败工具的错误信息都放回 messages，让模型自己决定怎么处理——是忽略失败的那个、重试、还是整体报错给用户。

-   **Q4：如何优化工具调用的总延迟？** 几个方向：识别关键路径（最长的串行依赖链），在关键路径上的工具优先优化；把能提前预测会用到的工具做异步预调用（Prefetch）；给高频工具结果加缓存，相同参数直接返回缓存；减少不必要的工具调用（在 description 里引导模型合并可以合并的操作）。

-   **Q5：多 Agent 场景和多工具场景有什么区别？** 多工具是同一个 Agent 在同一个上下文里调用不同工具，协调简单，上下文共享；多 Agent 是多个独立的 Agent 实例协作，每个 Agent 有自己的上下文，通过消息传递通信。多工具适合任务步骤明确的场景；多 Agent 适合任务可以完全独立拆分、或者需要专家分工的场景。
