# 10. 如何防止恶意输入攻击 Agent?

## 知识点讲解

### 1. 核心概念

恶意输入攻击是个大类，包含所有通过构造特定输入来破坏 Agent 正常行为的手段：Prompt 注入、越狱、长文本攻击（撑爆 context）、格式混淆（用 markdown/HTML 混淆指令）等。

防御恶意输入的核心思路是**不信任任何外部输入**——用户输入不信任，Agent 从外部系统获取的数据也不信任（因为攻击者可能控制那些外部系统）。

三个防御层：

1.  **输入层**：进来之前先过滤和校验

1.  **处理层**：LLM 和工具调用时加约束

1.  **输出层**：出去之前再检查一遍

### 2. 技术细节

#### 2.1 输入层的防御手段

**长度限制**

LLM 有上下文窗口限制，但超长输入可以：① 淹没系统 prompt（把系统指令稀释到几乎不可见）；② 造成大量 token 消耗（DoS 攻击）。设置合理的输入长度上限，超出就截断或拒绝。

**内容格式校验**

对于结构化输入（JSON、SQL、文件路径），在进入 LLM 之前做格式校验。格式不合法直接拒绝，不让 LLM 去"猜测"该怎么处理。

## 面试怎么答

> 防恶意输入攻击要做三层：输入层（进来之前就过滤）、处理层（LLM 处理时加约束）、输出层（出去之前再检查）。不信任任何外部输入，包括用户输入和 Agent 从外部系统获取的数据。
> 
> 输入层的核心措施：长度限制（防止淹没系统 prompt 和 DoS）；注入模式检测（正则匹配常见攻击模式）；编码检测（检测 Base64 等混淆手段）；速率限制（防止高频探测）。
> 
> 处理层：在系统 prompt 里明确告知 LLM 用户内容是"数据"不是"指令"，遇到可疑请求要拒绝。外部获取的数据（RAG 结果、API 返回）也要过验证器再注入 prompt，这是防间接注入的关键。

## 高频追问 & 加分点

-   **Q1：正则匹配注入模式准确率够吗？** 不够。正则只能匹配已知模式，攻击者会不断变体绕过。正则是第一层粗筛，不能作为唯一防线。更完整的方案：正则 + 专门的注入检测模型（有几个开源的可以用）+ LLM 自判断（让模型在处理前先判断输入是否有害）。

-   **Q2：用户用 Unicode 或 Emoji 混淆攻击怎么处理？** 先做文本规范化（Unicode NFKC normalization），把各种视觉相似的字符统一成标准形式，再做检测。比如全角字母 Ａ 和半角 A 长得一样，但字符码不同，规范化后统一处理。

-   **Q3：速率限制怎么设置才合理？** 没有统一标准，看业务场景。正常用户的使用频率是校准基线——P99 正常用户每分钟最多发 N 条请求，限制可以设在 2-3N。对于检测到可疑行为的用户（触发过注入告警），单独施加更严格的限制。限制不能太死，否则影响正常用户体验。

-   **Q4：如何应对精心构造的低频攻击（每天只试一两次，不触发速率限制）？** 靠速率限制防不住。需要行为模式分析：同一用户在不同时间提交的输入，是否有规律性地包含注入尝试？把多次尝试放在一起看（而不是每次独立判断），才能识别出低频但持续的探测行为。

-   **Q5：Agent 处理多模态输入（图片、文件）时有哪些特殊风险？** 几个值得注意的：图片里嵌入文字（Adversarial Optical Characters），图像识别模型读出来后注入到文本流；文件（PDF、Office）里嵌入的元数据或宏包含恶意指令；音频转文字后的内容包含注入。多模态输入的安全边界更难控制，处理多模态时每种模态的输出都要过对应的安全检测。
