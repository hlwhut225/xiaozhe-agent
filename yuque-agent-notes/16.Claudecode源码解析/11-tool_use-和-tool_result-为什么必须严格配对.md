# 11. tool_use 和 tool_result 为什么必须严格配对？

tool\_use 和 tool\_result 为什么必须严格配对？

Agent Loop 里有一个看起来很机械的规则：模型发出的每个 tool\_use，后面都必须有一个 ID 对应的 tool\_result。

很多人第一次实现时，会把它当成 API 格式要求。工具成功了就回传结果；工具失败、用户取消或者进程崩溃，就直接结束本轮。

这种实现通常能通过演示，却会在恢复会话、并行工具和中途取消时突然报错。更麻烦的是，损坏的历史可能被持久化，下一次恢复仍然报错，让整个会话“卡死”。

Claude Code 为配对规则写了执行、补偿和发送前修复三层保障。它告诉我们一件很重要的事：**工具调用 ID 不是展示用编号，而是一段 Agent 状态转换的事务键。**

如果只把它当成聊天内容，似乎少一条也没关系；如果把 Agent 看成状态机，就会发现 tool\_use 表示一个尚未结算的动作，tool\_result 表示这个动作被结算。

没有结果的调用会留下悬空状态。模型不知道动作没执行、执行到一半，还是结果丢了。之后它的任何推理都缺少确定前提。

## 为什么失败和拒绝也必须返回结果？

工具结果并不等于成功结果。只要一个 tool\_use 已经进入对话历史，它就需要一个可观察的结局。

这不是为了迎合协议，而是给模型提供纠错信息：

-   未知工具：重新选择当前可用工具。

-   参数错误：修正字段类型或补齐字段。

-   权限拒绝：停止该路径，或者向用户解释限制。

-   执行失败：分析错误并决定是否重试。

-   用户取消：不要假设原动作已经生效。

如果异常直接穿透 Agent Loop，模型失去了修复机会；如果错误结果仍然带上调用 ID，失败就成为下一轮推理可以使用的观察值。

## 中断发生在一半时，怎样补齐配对？

普通路径不知道哪些工具已经开始，因此对当前响应里的调用统一补结果。流式执行器跟踪了每个工具的 queued / executing / completed / yielded 状态，能够给排队中和执行中的工具生成更准确的合成错误。

这里的设计原则是：**取消不是删除历史，而是为已经公开的动作写入取消结局。**

## 为什么结果必须紧跟对应的调用批次？

配对不只要求 ID 相等，还涉及消息顺序。

当一个 assistant 消息里包含多个 tool\_use 时，下一条 user 消息通常承载这一批工具结果。不能随意在它们中间插入普通用户文本，否则 API 可能无法判断哪些结果属于哪次工具轨迹。

Claude Code 的查询循环有一段注释直接指出：如果在 tool\_result 消息和普通用户消息之间错误交错，API 会拒绝。

这和数据库事务日志很像：真实执行完成顺序可能不同，提交日志仍要让消费者得到一致、可重放的状态序列。

## 会话恢复时，历史为什么会损坏？

理想路径里执行器总会产生结果，但真实系统还有远程会话、进程退出、版本迁移、消息压缩和持久化失败。

常见损坏包括：

1.  tool\_use 已写入，tool\_result 还没写入进程就退出。

1.  压缩或恢复时丢了调用消息，只剩结果。

1.  同一段孤儿处理逻辑重复运行，产生重复 ID。

1.  流式重试产生了新调用，却混入上一次尝试的旧结果。

1.  恢复从会话中段开始，第一条就是找不到来源的结果。
