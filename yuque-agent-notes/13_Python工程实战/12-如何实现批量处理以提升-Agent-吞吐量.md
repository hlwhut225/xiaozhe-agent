# 12. 如何实现批量处理以提升 Agent 吞吐量？

## 知识点讲解

### 1. 核心概念

批量处理（Batching）是吞吐量优化的核心手段——把多个单独请求合并成一批，一次提交，分摊固定开销。

固定开销包括：网络往返（RTT）、连接建立、API 服务端的调度开销。单条请求每次都要付这些成本；批量处理把这个成本摊给 N 条请求，每条请求的平均开销就降到了 1/N。

Agent 里批量处理的主要场景：

-   **批量 embedding**：给 100 条文档生成向量，逐条调用 API 要 100 次 RTT，批量只需几次

-   **批量 LLM 推理**：Anthropic 的 Batch API 支持最多 10 万条请求打包，成本降 50%

-   **批量数据库写入**：把向量一批插入而不是逐条 upsert

### 2. 技术细节

批大小（batch\_size）是核心参数，有个权衡：

-   太小：固定开销没被充分摊销，吞吐量提升有限

-   太大：单批延迟高，用户等待时间长；API 可能有单次请求大小限制

OpenAI Embedding API 单次最多 2048 条文本；Anthropic Batch API 单次最多 10000 条请求。实践中 embedding 批大小 50-200，LLM 推理根据 API 限制决定。

**动态批大小**：负载低时攒小批及时处理，负载高时攒大批降低成本。用队列 + 超时触发实现。

### 3. 对比与拓展

批处理 vs 流处理：批处理优先吞吐量（后台任务、离线处理）；流处理优先实时性（在线对话）。Agent 的离线评估、文档摄取适合批处理；实时对话步骤适合流处理。

## 面试怎么答

> 批量处理的本质是把多次请求的固定开销（网络往返、连接建立）摊销到多条数据上。单条 embedding 和 100 条 embedding 的网络开销差不多，但吞吐量差了 100 倍。
> 
> 批大小是关键参数：太小摊不了成本，太大单次延迟高、还可能超 API 限制。我一般从 32-64 开始测，找到吞吐量和延迟的平衡点。
> 
> 实时场景用动态批处理——攒够 batch\_size 或者超时（比如 500ms）就触发，这样低负载时也能及时响应，高负载时自动批量。离线场景用 Anthropic Batch API，成本直接降一半，缺点是有最长 24 小时的延迟，适合离线评估和文档预处理。

## 高频追问 & 加分点

-   **Q1：如何确定最优的 batch\_size？** 做基准测试：固定总请求数，测不同 batch\_size 下的吞吐量（requests/s）和 P99 延迟。通常吞吐量在某个 batch\_size 后趋于平稳，而延迟在这之后开始明显上升——那个拐点就是最优值。API 有硬上限（如 OpenAI embedding 单批 2048）要提前确认。

-   **Q2：批处理中部分失败怎么处理？** 单独重试失败的条目，不要整批重试（成本翻倍）。记录失败条目的 index 和错误原因，重试时用指数退避。如果是 rate limit 错误，整批降速重试；如果是特定条目导致的错误（比如文本太长），只针对那几条处理（截断或跳过）。

-   **Q3：向量数据库批量写入有什么注意事项？** ChromaDB 建议每批 100-1000 条；Pinecone 建议每批不超过 100 条（每条最多 40KB）；写入前先做去重（相同 id 的 upsert 会覆盖）。批量写入时用 asyncio.gather + Semaphore 控制并发，避免超过数据库连接上限。

-   **Q4：批处理和流式处理能结合吗？** 可以，这是"微批"（micro-batch）的思路。流式收数据，积攒到一定量或一定时间就处理一批。Spark Streaming 就是这个模式。在 Agent 里，实时对话里的 embedding 调用可以用微批：收到用户消息后立刻触发，但如果同时有多个用户消息，合并成一批发 API。
