# 20. 如何用 Python 实现多轮对话管理？

## 知识点讲解

### 1. 核心概念

LLM 本身是无状态的——每次调用它看不到之前说了什么。多轮对话的"记忆"完全靠**把历史消息列表传给 LLM**来模拟。

### 2. 技术细节

多轮对话的三个核心问题：

**① Token 溢出**：消息列表随对话增长，最终超过 LLM 的 context window 限制。常见策略：

-   滑动窗口：只保留最近 N 轮

-   历史压缩：让 LLM 把旧对话总结成一段话，替换掉原来的长历史

-   向量记忆：把历史存向量库，检索时只取相关的几条

**② 会话隔离**：多用户并发时，每个用户的对话历史必须互相独立，不能串。用 session\_id 做索引，每个 session 有自己的消息列表。

**③ 持久化**：服务重启后历史不丢失。开发期存 Redis（快），生产期存数据库（PostgreSQL、MongoDB）。

### 3. 对比与拓展

短对话（≤10 轮）：简单列表存历史，直接传 LLM。 长对话（>20 轮）：必须有压缩或外部记忆机制，否则 context 溢出。 Agent 的工具调用历史：工具调用消息格式特殊（tool\_use + tool\_result），要按 LLM SDK 的格式存，不能随意截断。

## 面试怎么答

> LLM 是无状态的，多轮对话的"记忆"靠把历史消息列表一起传给 LLM 来实现。每轮交互后把 user 和 assistant 消息追加进列表，下轮调用时把整个列表发过去，LLM 就能理解上下文了。
> 
> 工程上有三个问题要解决。一是 token 溢出：历史越积越长，超过 context window 就报错——常见策略是滑动窗口（丢最旧的轮次）或历史压缩（让 LLM 把旧对话总结替换）；二是会话隔离：多用户并发时用 session\_id 做 key，每个 session 独立一份历史；三是持久化：服务重启不丢历史，存 Redis 或数据库。
> 
> Agent 的工具调用消息格式比普通对话复杂——有 tool\_use 和 tool\_result 这两种特殊消息，截断历史时要注意配对完整，不能把 tool\_use 和它对应的 tool\_result 拆开，否则 LLM 会报错。

## 高频追问 & 加分点

-   **Q1：历史压缩会丢失信息吗？怎么权衡？** 会，这是不可避免的代价。权衡点是：保留多少最近原文（recent\_keep）和总结质量之间的平衡。实践中 recent\_keep=4-6 轮原文 + LLM 总结旧部分，既保住上下文连贯性，又控制了 token 消耗。关键信息（比如用户说的具体需求）要放在总结里显式保留，不能让 LLM 自由发挥删掉重要内容。

-   **Q2：用向量记忆替代完整历史有什么优缺点？** 优点：理论上无限长的"记忆"，每次只检索相关历史，token 可控。缺点：检索不一定准，可能漏掉重要上下文；对话的时间顺序关系容易丢失；实现复杂。适合长期记忆（比如 Agent 跨会话记住用户偏好），不适合短期的当前对话上下文（还是传完整历史更可靠）。

-   **Q3：tool\_use 和 tool\_result 消息必须配对吗？** 是的，Anthropic API 严格要求：每个 tool\_use block 必须有对应的 tool\_result（用 tool\_use\_id 关联）。如果截断历史把一个 tool\_use 留下来但把它的 tool\_result 切掉，下次调用 API 会报 400 错误。安全的截断策略：在一轮完整的 user + assistant 对话边界截断，不要在工具调用中间截。

-   **Q4：如何跨会话持久化对话历史？** 开发：Redis（session\_id 为 key，消息列表序列化后存，设 TTL 自动过期）；生产：关系型数据库（PostgreSQL，一个 messages 表，session\_id + turn\_index + role + content），查询时 WHERE session\_id=? ORDER BY turn\_index。消息要加 created\_at 时间戳，方便排查问题和对话复现。
