# 7. 如何设计稳定可靠的 Prompt？

## 知识点讲解

### 1. 核心概念

稳定可靠的 Prompt 指的是：**同一输入多次调用，输出结构和质量一致；面对输入变化，仍能正确处理，不会因为细节差异就完全崩掉**。

这是把提示词工程从"碰运气"变成"工程实践"的关键。

稳定性有三个层次：

1.  **格式稳定**：每次输出的结构一致，可以被解析

1.  **语义稳定**：同样的问题得到实质相同的答案

1.  **边界稳定**：异常输入不会导致模型崩掉或输出垃圾

### 2. 技术细节

#### 2.1 影响稳定性的关键因素

**① 指令清晰度** 模糊指令 → 模型解读空间大 → 输出方差高。命令式的明确指令比"请试着..."这类表达稳定得多。

**② 输出格式显式约束** 没有格式约束的 prompt，模型每次可能输出不同结构。明确指定格式（JSON Schema、Markdown 结构）是最有效的稳定手段。

**③ Few-shot 示例** 示例是最有效的"锚点"，让模型的输出向示例风格收敛。

**④ Temperature** 降低 Temperature 直接降低随机性。稳定性要求高的任务通常用 0.1-0.3。

**⑤ 错误处理声明** 在 prompt 里告诉模型"无法完成时怎么办"，防止它乱编答案。

#### 2.2 稳定性测试方法

-   **一致性测试**：同一 prompt 运行 10 次，计算输出相似度

-   **输入敏感性测试**：对 prompt 做微小变化，观察输出是否剧变

-   **边界测试**：输入空值、极端值、格式错误的输入，看模型怎么处理

## 面试怎么答

> 设计稳定可靠的 prompt 有几个核心要点：指令要清晰（用命令式而不是"请试试"），输出格式要显式约束（JSON Schema 或 Markdown 结构），加 Few-shot 示例作为锚点，告诉模型"不能完成时怎么办"（防止乱编），然后把 temperature 降低。
> 
> 工程上我习惯做三层测试：一致性测试（同一 prompt 跑 10 次，看输出有多稳定）、输入敏感性测试（微小改动看有没有剧烈变化）、边界测试（空值、异常格式的输入）。稳定性不是主观感觉，要量化。
> 
> 还有一点：在应用层做格式验证 + 重试。prompt 再好，偶尔也会格式出错，不能假设模型 100% 遵守约束。有了验证层，失败了重试一次，整体可靠性就高很多。

## 高频追问 & 加分点

-   **Q1：Temperature=0 是不是最稳定？** 是，但不一定最优。Temperature=0 退化成贪心搜索，输出最确定，但对于需要一点语言多样性的任务（比如写摘要），效果可能反而死板。通常 0.1-0.2 是稳定性和自然度的平衡点。

-   **Q2：JSON 格式约束可靠吗？** 不是 100%。模型偶尔会在 JSON 前后加多余文字，或者忽略某些字段。最稳定的方式是用支持 Structured Output 的 API（OpenAI 的 response\_format={"type":"json\_object"}），或者用 function calling——这两种方式在模型层面就保证格式，不依赖 prompt 约束。

-   **Q3：Prompt 版本怎么管理？** 像代码一样：用 git 管版本、有 changelog、每次改动都跑测试集对比效果。如果 prompt 是产品的核心，更应该有专门的评估框架，而不是主观判断"感觉好了一点"。

-   **Q4：同一 prompt 在不同时间结果差很多是为什么？** 几个可能原因：模型版本更新（API 背后的模型偷偷升级了）、采样随机性（temperature 不够低）、prompt 有歧义（模型可以用不同方式解读）。前两个靠固定模型版本 + 低温解决，第三个要回到 prompt 设计本身。
