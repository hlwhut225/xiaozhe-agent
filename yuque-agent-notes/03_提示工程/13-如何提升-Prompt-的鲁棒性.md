# 13. 如何提升 Prompt 的鲁棒性？

## 知识点讲解

### 1. 核心概念

Prompt 的鲁棒性，指的是面对各种输入变化时，输出质量能保持稳定，不因为输入的细小差异就崩掉。

一个脆弱的 prompt：精心构造的测试案例下表现完美，但只要用户输入稍微偏一点——多了个换行、缺了个字段、用了繁体——就输出垃圾。

鲁棒性有三个层次：

1.  **格式鲁棒**：输入格式变化，输出格式依然正确

1.  **语义鲁棒**：相同意思的不同表达，得到实质相同的答案

1.  **边界鲁棒**：空输入、超长输入、恶意输入，不导致系统崩溃或乱输出

### 2. 技术细节

#### 2.1 提升鲁棒性的核心手段

**① 示例要覆盖边界**

Few-shot 示例只选"理想输入"是最常见的失误。边界情况的示例才是关键：

-   输入为空时怎么处理

-   输入超短/超长时怎么说

-   输入信息不足时，应该拒绝还是猜

**② 在 prompt 里写清楚失败策略**

告诉模型"如果无法完成，直接说无法完成"。不写的话，模型倾向于强行给答案，出现幻觉。

**③ 应用层做重试 + 验证**

格式验证不通过 → 把错误反馈给模型 → 要求重新生成。这比单纯重试效果好，因为模型拿到了自己的错误，能针对性修正。

**④ 温度参数控制**

生产场景的鲁棒性需求，temperature 一般控制在 0.1-0.3。不是 0，因为 0 有时候太死板；不超过 0.5，因为随机性太大就不稳了。

#### 2.2 压力测试方法

-   **一致性测试**：同一 prompt 运行 10 次，看输出方差

-   **输入扰动测试**：加个标点、改个词序，输出是否剧变

-   **边界测试**：空值、极端长度、纯符号输入

-   **对抗测试**：用户故意给"刁难"输入，模型怎么处理

## 面试怎么答

> 提升 Prompt 鲁棒性，我从三个角度来做。
> 
> prompt 设计层面：Few-shot 示例要覆盖边界情况，而不只选理想输入；显式告诉模型"如果无法完成，直接说做不到"——这个声明能大幅减少模型强行输出垃圾的概率。
> 
> 应用层：格式验证 + 重试。验证失败时不是盲目重试，而是把错误反馈给模型，让它针对性修正，效果比纯重试好得多。另外给高风险调用加降级方案，主路径挂了还能走规则或简化 prompt 兜底。
> 
> 测试层面：跑一致性测试（同 prompt 多次运行，看输出方差），跑边界测试（空输入、超长输入、纯符号）。鲁棒性不能靠主观感觉，要量化。

## 高频追问 & 加分点

-   **Q1：鲁棒性测试应该用多少个测试样本？** 一致性测试跑 10 次就够了，主要看格式失败率和语义漂移程度。边界测试要尽量穷举边界类型，数量不重要，覆盖面重要。如果是上线前的系统验收，建议准备 50-100 条有代表性的输入（含正常、边界、异常），通过率 95% 以上才放行。

-   **Q2：温度设为 0 不就最稳定了吗？** 理论上是，实际上 temperature=0 是贪心搜索，输出有时候会过于死板——对于需要稍微灵活表达的任务（摘要、分析）效果反而差。0.1-0.2 是大多数场景的平衡点：随机性低，又不至于僵硬。

-   **Q3：如何处理用户输入语言不同的情况？** 两个策略：① 在 system prompt 里声明"无论输入是什么语言，输出一律用中文"，让模型自己处理语言差异；② 在应用层预处理，先检测/翻译输入再送入 prompt。前者简单省事，后者控制力更强。高鲁棒性要求的系统建议用后者，至少对语言类型做检测。

-   **Q4：验证失败后重试，会无限循环吗？** 要给重试次数设上限，通常 2-3 次够了。重试超出上限后要么走降级方案，要么抛出明确的错误给上层处理，绝对不能无限重试。每次重试把当前错误反馈给模型，基本两次就能修正大多数格式问题。
